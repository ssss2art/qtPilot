# MCP `2026-07-28` migration — gap analysis and plan

**Branch:** `feat/mcp-2026-07-28` · **Opened:** 2026-08-01 · **Status:** exploration

This is a long-lived exploration branch. It is **not** intended to merge to `main`
until the upstream SDK leaves beta. The goal is to prove out the `2026-07-28`
revision against qtPilot's actual architecture and find out what breaks.

---

## 1. What `2026-07-28` is

The [`2026-07-28` revision](https://modelcontextprotocol.io/specification/2026-07-28)
is the largest change to MCP since launch. It converts MCP from a **stateful,
bidirectional, session-oriented** protocol into a **stateless request/response**
protocol.

Changes that matter to qtPilot, in rough order of impact:

| # | Change | qtPilot impact |
|---|--------|----------------|
| 1 | **`initialize`/`notifications/initialized` handshake removed.** Every request carries its own protocol version and client capabilities in `_meta`. | None directly — qtPilot implements no wire protocol. Handled by the SDK. |
| 2 | **Protocol sessions and `Mcp-Session-Id` removed.** List endpoints no longer vary per-connection. | **High.** See §3 — qtPilot's mode switching mutates the tool list at runtime. |
| 3 | **`server/discover` is now a mandatory RPC.** | SDK-provided. Confirm it is actually served once on fastmcp 4. |
| 4 | **`CacheableResult`** — `ttlMs` + `cacheScope` required on `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list`. | **Medium.** qtPilot serves `qtpilot://status`, whose whole value is that it is *not* cacheable. See §4. |
| 5 | **`tools/list` SHOULD be deterministically ordered** (client-side caching, prompt-cache hit rates). | **Medium.** qtPilot's order is currently registration order, which varies with mode. |
| 6 | **All results carry a required `resultType`** (`"complete"` / `"input_required"`). | SDK-provided. |
| 7 | **Logging, Roots, and Sampling deprecated** (12-month window). | **Low** — see §5, qtPilot's "logging" is its own thing. |
| 8 | **`ping` and `logging/setLevel` removed.** | **None.** qtPilot's `qt_ping` is a qtPilot tool, not MCP `ping`. |
| 9 | Multi Round-Trip Requests (MRTR) replace server-initiated requests. | None — qtPilot initiates nothing toward the client. |
| 10 | HTTP+SSE reclassified Deprecated; SSE resumability removed. | **None.** qtPilot is stdio-only. |
| 11 | Resource-not-found error code `-32002` → `-32602`. | SDK-provided. |

Two changes are worth calling out as *non-issues* despite sounding alarming.
qtPilot is **stdio-only** — one server process per client — so removing
protocol-level sessions does not, by itself, invalidate qtPilot's model of
"connect to a probe once, then call tools against it". That state lives in the
server *process* (the FastMCP lifespan), not in an MCP session. The spec's
statelessness requirement is about the wire, and qtPilot's wire state was always
incidental.

## 2. SDK reality check

Verified empirically on 2026-08-01 by installing each into a clean venv and
reading `mcp.types.LATEST_PROTOCOL_VERSION`:

| Package set | Advertises | Notes |
|---|---|---|
| `fastmcp` 2.14.7 / `mcp` 1.28.1 | `2025-11-25` | what `main` currently resolves |
| `fastmcp` 3.4.5 / `mcp` 1.29.0 | `2025-11-25` | **3.x does not move the protocol** |
| `fastmcp` 4.0.0b1 / `mcp` 2.0.0 | **`2026-07-28`** | beta, released 2026-07-28 |

So `2026-07-28` support requires **fastmcp 4**, currently in beta. FastMCP's own
framing of the 4.0 release is that it makes "stateful MCP applications work on
the sessionless protocol" — which is precisely qtPilot's situation.

`main` pins `fastmcp>=2.9,<3`, so it cannot even reach 3.x today.

## 3. The real problem: qtPilot's tool surface mutates at runtime

This is the finding that actually forces work.

`qtpilot_set_mode` changes which tool families are exposed (`qt_*`, `chr_*`,
`cu_*`) by **adding and removing tools on the live server**:

- `_has_tools_with_prefix()` and `_remove_tools_by_prefixes()` in
  `python/src/qtpilot/server.py` iterate `mcp._tool_manager._tools` — a **private
  attribute**.
- Removal goes through `mcp.remove_tool(name)`.

Both of these are already broken upstream, independent of the protocol revision:

| API | fastmcp 2.14.7 | fastmcp 3.4.5 | fastmcp 4.0.0b1 |
|---|---|---|---|
| `FastMCP._tool_manager` | present | **gone** | **gone** |
| `FastMCP.remove_tool` | present | present | **gone** |

So the current implementation is hard-blocked at fastmcp 2.x. Upgrading is not
optional-with-benefits; the dynamic-mode machinery has to be rewritten either way.

The spec pushes the same direction. Under `2026-07-28`, `tools/list` results are
cacheable (`ttlMs`/`cacheScope`), no longer vary per-connection, and should be
deterministically ordered. A tool surface that mutates in response to a tool call
is in tension with all three.

**Proposed replacement:** register every tool family once, at startup, and use
FastMCP 3/4's **transform** layer to control which are *visible* per mode.
`fastmcp.server.transforms` exposes `Transform`, `ToolTransform`, `Visibility`,
and `is_enabled` — visibility filtering over a static registration set. This
gives a stable, deterministically-ordered tool list whose *exposure* is
configuration, and removes all private-attribute access.

Open question: whether a visibility transform can be re-evaluated at runtime by
`qtpilot_set_mode`, or whether mode must become launch-time configuration only
(`qtpilot serve --mode ...`, already supported) with `listChanged` emitted on
change. The latter is more spec-aligned; the former preserves current UX. This
branch should try the transform route first and measure what a client actually
does with the resulting `listChanged` + cache invalidation.

## 4. `qtpilot://status` and cacheability — **resolved, no code change needed**

`register_status_resource()` serves `qtpilot://status` — live probe connection
state (connected, ws_url, mode, discovered probe count). Under `2026-07-28`,
`resources/read` results carry required `ttlMs` and `cacheScope`.

This resource is the definition of non-cacheable: it exists to report state that
changes underneath the client. The open question was what fastmcp 4 defaults to,
and whether qtPilot needed to override it.

**Verified 2026-08-01 against fastmcp 4.0.0b1 / mcp 2.0.0** — the SDK defaults
are already correct, and FastMCP does not override them:

| Result | `ttlMs` | `cacheScope` |
|---|---|---|
| `resources/read` (`qtpilot://status`) | `0` | `private` |
| `resources/list` | `0` | `private` |
| `tools/list` | `0` | `private` |

`ttlMs: 0` means "do not cache"; `cacheScope: "private"` keeps shared
intermediaries out of it. So there is **no staleness bug** and no override to
write. `fastmcp.FastMCP.resource()` exposes no ttl/cache parameter anyway — the
values come from the `CacheableResult` field defaults in `mcp.types`.

What was missing was anything *holding* that guarantee. `tests/test_status_resource.py`
now asserts the policy directly, so a future SDK bump that introduces a non-zero
default TTL fails the suite instead of silently letting clients serve stale probe
connection state. The tests skip on pre-`2026-07-28` SDKs, where the fields do
not exist.

Note also that `docs/MCP-CONFORMANCE.md` previously claimed qtPilot exposes
"**tools** only ... does not implement MCP `resources` or `prompts`". That was
inaccurate — this resource has existed alongside it. Corrected on this branch.

### Deterministic `tools/list` ordering

Checked at the same time, since it is the other half of the caching story.
qtPilot's tool order is **already deterministic**: tools are registered in a
fixed sequence from `_register_tools_for_mode`, and two servers constructed with
the same mode produce identical `tools/list` order. Covered by a regression test
rather than left as an assumption. No change needed.

## 5. Deprecations — mostly a false alarm

The spec deprecates **Logging**. qtPilot has `logging_middleware.py`,
`message_logger.py`, and `qtpilot_log_*` tools, so this looks like a direct hit.
It is not: those implement qtPilot's **own** JSONL capture of probe traffic,
exposed as ordinary tools and written to a file. They do not use MCP
`logging/setLevel` or `notifications/message`. No migration required.

**Roots** and **Sampling** are unused. **Dynamic Client Registration** and the
OAuth changes are unused — qtPilot is stdio-only with no auth. **HTTP+SSE**
deprecation is likewise moot.

The one thing to watch: FastMCP 3.x's release notes state "server-initiated
sampling and roots are removed from the server API". qtPilot doesn't use them, so
this should be a no-op, but it's worth confirming nothing in the middleware path
depends on them.

## 6. Compatibility strategy

Requirement for this branch: **keep the existing install working**. Users on
`pip install qtpilot` today must not be broken by exploration, and the new path
should only take over for new installs, if and when this lands.

Approach:

1. A compatibility shim (`_mcp_compat.py`) that detects the resolved SDK
   generation and adapts the handful of places qtPilot touches version-specific
   API — principally tool enumeration and mode switching. No private attributes.
2. Dependency ranges that let both generations resolve, with the legacy path as
   the default resolve and the new path selected explicitly.
3. `uvx` as the documented entry point for new installs, which sidesteps the
   whole "which SDK generation is in your environment" problem by giving each
   invocation an isolated, locked resolution.
